# Discover sessions

Discover reads live public occurrences through `discover_sessions_by_city` (older RPC signatures remain compatible). It does not expose draft series, private occurrences, roster identities or unpublished venues/organizers. The private implementation and public security-definer entry point use an empty search path and an explicit field projection. Base-table RLS stays unchanged. Anonymous access is intentional, matching public session details; Supabase's definer advisories are expected for this narrow public API ([advisory](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)).

## Eligibility and filters

Only future published sessions at active venues, hosted by active organizers, whose registration window is open appear. The default includes open confirmed places, available waitlist places, and the viewer's own confirmed/waitlisted or hosted public sessions. Full sessions can be included explicitly with All sessions. Category matches the session's allowed categories; it does not assert that the viewer passes strict registration checks.

Search matches literal session titles and venue names. Structured city selection uses a catalog ID and a disclosed 25 km area around the city center; legacy free-text preferences continue to match saved venue names/addresses until replaced. Location is remembered locally. See Structured city search and Distance radius below. Filters combine date/date range, category, morning (before noon), afternoon (noon–18:00), evening (18:00 onward), and availability. Dates/times follow the occurrence's series timezone, defaulting to Buenos Aires. The date picker currently follows the app's Buenos Aires convention.

The chronological response is bounded to 500 results. A visible notice asks users to narrow their search if more match. No silent pagination or invented recommendations. Starting soon means the next three hours (first six in the carousel, all via See all); Available today covers the remainder of the local day; Upcoming covers later days. These sections do not duplicate occurrences. Search and explicit filters show one chronological list.

Cards use existing session covers and venue Google Maps photo fallback with required credits; a neutral placeholder appears when no photo exists. They show real price, category and availability or the viewer's Registered/Waitlisted/Hosting status. Card taps open the existing public occurrence detail. Registration/cancellation and organizer session changes invalidate discovery. Focus, foreground return, polling and pull-to-refresh update inventory.

## Header and map control

Discover replaces the shared header wordmark with the current location selector; it opens the existing location sheet. Other tabs retain the Palla wordmark and notification button. The map/list switch is a 56-point circular icon-only button with explicit accessible labels. List and map show the same reusable search bar and filter chips, backed by the same search draft and applied filters. Map view fills the full width and height between the navigation header and bottom tabs. The search bar and horizontally scrolling filter chips float over the map at the top; the circular Map/List button floats at the bottom right above the map credits. Camera padding follows the measured controls so markers stay clear of them. Map view omits the extra section heading and Edit filters action.

## Map

The Map button switches the same search into a native WebView containing the existing minimal MapLibre/OpenFreeMap street style. The list stays mounted so its scroll position survives switching views. Markers group matching occurrences by venue; tapping selects that venue’s first matching occurrence in a compact, swipeable card carousel. Cards show a side image, availability over the photo, title, venue and schedule with icons, a text-only category chip, and price. Swiping updates the highlighted marker and camera; tapping a card opens public details. The List toggle and camera padding move above the measured carousel height. Android Back dismisses the selected cards. The circular List toggle returns to the accessible session list. Details navigation remains the existing public session route.

Venue latitude/longitude are stored on `venues` with the matched address and timestamp, and included in both discovery and public-detail responses. Browsing never calls an address-geocoding provider. The publishing service looks up missing coordinates through the existing Photon adapter, requiring a matching street and house number (and city when returned), and accepts no street/city centroid. Provider failure does not block publishing. Stored pairs are reused; only an active creator can fill a missing pair through the private publishing helper, existing pins cannot be overwritten, and changing the address clears stale coordinates. Unlocated venues remain available in the list and public detail retains Open in Maps. Map-tile failures have a retry state; a slow map times out after 25 seconds. Map browsing itself makes no location permission requests. City detection, Nearest sorting and distance radius request foreground permission only on explicit selection.

Panning exposes Search this area. Applying it filters the shared result set to venues with saved coordinates within those bounds; Changing filters, or using Clear filters in list view, clears the map area. This initial implementation searches the already fetched, bounded results, with the same result-limit notice; it is not a server-side geospatial index.

### Advanced filters

The shared **More filters** sheet supports an inclusive min/max price per player (ARS), Covered/Uncovered, gender policy, session inclusions and venue facilities. Blank bounds mean any price; maximum `0` finds free sessions. Decimal commas and dots are accepted; negative/reversed/overflowing bounds are rejected before applying. Larger text stacks price inputs vertically. A fixed Apply/Reset footer remains usable with the keyboard; validation errors are repeated there if the price fields have scrolled away.

Changes stay local until Apply. Closing/back discards the draft. Reset clears only the advanced draft, while the page's Clear filters clears every filter except location. List and map use the same applied state and query; changing filters clears the previous map area/selection.

`discover_sessions_filtered` applies all predicates **before** the 500-result limit. The original seven-argument RPC delegates to the same private core, preserving installed-client behavior. The public wrapper intentionally uses a restricted security-definer projection for unauthenticated discovery, with an empty search path; the private core and base tables stay inaccessible. Its security-advisor public-execution warning is expected for this public API.

Coverage uses the actual occurrence's `court_coverage`; unknown values do not match an explicit roof filter, even when the venue offers both. “Any gender” does not filter; “All genders” matches that policy exactly. All selected attributes must match; `new_balls` also satisfies `balls_provided`. Venue facilities are correlated to **both the session's organizer and venue**, so another host's claims cannot satisfy a filter. Price bounds also require matching currency. These filters do not override registration eligibility.

Regression: `supabase/tests/discovery-advanced-filters.sql` rolls back all fixtures and tests price boundaries, currencies, coverage, gender, all-of attributes, host-specific amenities, invalid input, combined filters, private-core grants, pagination-before-filter regressions and legacy RPC compatibility. `advanced-filters.test.ts` verifies price parsing and active-filter state.

## Sorting

The shared filter row includes an anchored **Sort** menu: Soonest (default), Lowest price and Nearest to me. Soonest retains the chronological discovery sections. Other sorts show one ranked list; the screen preserves server order instead of regrouping it chronologically. Map markers still group by venue, but the swipeable cards retain the global result order across venues. Time and occurrence ID break price/distance ties deterministically; free sessions sort first by price (the current database supports ARS).

`discover_sessions_ranked` filters and sorts **before** the 501-candidate/500-result page and JSON aggregation. Both previous RPC signatures delegate to the same private core with Soonest. The same published/public/open-registration projection, active organizer/venue checks, grants and base-table privacy remain. Anonymous security-definer execution is intentional for this narrow public-discovery endpoint ([advisor rationale](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)).

Nearest requests a single foreground device location only after that option is selected. It uses a recent fix (at most 60 seconds old, within 1 km reported accuracy) or requests a GPS-capable foreground fix without prompting to enable network location accuracy, with a 20-second UI timeout. Denial, disabled services or failure leave the previous sort active and show an actionable inline message. Choosing another sort ignores any pending location response. The origin stays in memory/query state, is sent to the RPC to calculate straight-line great-circle distance, and is not saved to a user or venue record. Selecting Nearest again refreshes the origin; there is no continuous/background tracking.

Existing city/search/date/attribute filters still apply; selecting Nearest does not change the chosen search area or impose a radius. Venues without coordinates appear last, with `distance_m=null`. Invalid/incomplete origins or Nearest without an origin are rejected by the RPC. Current results and filter drafts remain intact while locating; loading/error feedback is shared by the list and map controls.

Regression: `supabase/tests/discovery-sorting.sql` verifies ranking, free sessions, distance calculation, missing coordinates, deterministic ties, ranking with filters, invalid inputs, private-core permissions, legacy compatibility and cheapest/nearest results beyond the first 500 chronological sessions. `discovery-location.service.test.ts` checks valid/invalid fixes, permission failures and timeout handling. Native presentation fixtures use `rankPreviewSessions` only for QA; production sorting is always database-side.

## Distance radius

The shared filter row offers **Any distance**, **Within 5 km**, **Within 10 km**, and **Within 25 km**. A bounded radius searches around one foreground device location and shows **Near me** in the header; it replaces the saved text city/area predicate rather than accidentally intersecting a nearby search with a different city. All other filters still combine. Clearing the radius restores the saved city. Choosing a city explicitly disables the radius. Clear filters resets radius, sorting and origin together.

Radius and Nearest sorting share one in-memory origin and one pending native fix. First enabling a radius requests location; changing an active radius reuses its center. Switching from Nearest to price/time retains the origin while a radius needs it; clearing radius retains it only if Nearest still needs it. Reselecting Nearest refreshes the shared center. Denial/failure leaves the previous state unchanged. Changing the selected city or clearing filters cancels pending UI updates, and a newer sort/radius choice wins over an older location request. No location tracking or persisted user-location record is added.

The new `discover_sessions_nearby` endpoint accepts `p_radius_km` (NULL, 5, 10 or 25). All older discovery RPC signatures remain intact and delegate to the same private core with no radius. Filtering uses the great-circle `distance_m` **before** candidate/page limits, independent of the chosen sorting; unknown venue coordinates are excluded from a bounded-radius search. The supplied origin must be a valid pair. Distances are straight-line distances, not road/travel distances. Base-table RLS and the explicit public projection remain unchanged; public security-definer execution is intentional for this public search ([advisory](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)).

`supabase/tests/discovery-radius.sql` rolls back every fixture and covers just-inside/just-outside distances for all three radii, saved-city replacement, combined coverage/price/nearest filters, unknown coordinates, invalid radii/origins, privacy/grants, old-client defaults, and a later matching occurrence behind 501 earlier out-of-radius occurrences. `radius.test.ts` checks supported choices and read-only fixture filtering. Production distance filtering always runs in the database.

## Structured city search

The header location sheet now provides a single worldwide city search and **Use my location**. There is no separate country step. Typing at least two letters performs a debounced, cancellable database search, returning at most eight cities with region and country for disambiguation. Selecting a result shows confirmation; **Use this city** applies it. Closing or Android Back discards the draft. Empty, loading, network failure/retry, GPS denial, disabled services and detection failure have explicit states.

The catalog is GeoNames `cities500` (cities/towns with population over 500 or qualifying administrative seats), not every named settlement or neighborhood worldwide. Source: <https://download.geonames.org/export/dump/readme.txt>. Public geographic reference data uses the CC BY 4.0 license; the picker links to GeoNames with attribution. `scripts/prepare-discovery-cities.py --output <directory>` downloads the current public city/country/admin files and prepares idempotent SQL upserts. Apply these batches through the connected Supabase SQL tool or an authorized CLI connection after the schema migration. Refresh periodically; upstream deletions are not automatically applied. Catalog data is hosted in `private.discovery_cities`, inaccessible directly to app roles. Narrow public read-only RPCs expose only bounded search results and one nearby city; private reference-data RLS is enabled with no client write grants.

**Use my location** requests one foreground GPS fix only on tap, then resolves the nearest catalog city within 50 km through the backend. It is a suggested city, so the user must confirm or search for a different one. Existing GPS acquisition is bounded to 20 seconds and the reverse lookup to a further 10 seconds. Editing/searching or dismissing ignores a late detection. Precise GPS coordinates are transient request data, never stored in the city preference or a profile. No third-party reverse geocoder or background tracking is added.

The selected catalog ID, city name, region, country code/name and city-center coordinates are stored locally in a versioned, validated record. A prior free-text location remains active until the user selects a structured city. Invalid stored records safely fall back to the legacy preference or initial Buenos Aires default. Storage errors keep the picker open for retry. The app never auto-overwrites a manually chosen city on launch.

`discover_sessions_by_city` takes the city ID and uses trusted catalog coordinates to select venues within **25 km of the city center**, before sorting and the 500-result cap. This is a proximity area, not an administrative city boundary. The current compact picker omits the explanatory radius copy. Unknown venue coordinates cannot match a structured city. Session title/venue search and all other filters still combine. Existing legacy text discovery RPCs remain compatible. A GPS distance radius overrides the city area and clearing it restores the saved city; Clear filters preserves the city. Anonymous search intentionally uses a narrow security-definer API with an empty search path, while private tables/cores remain inaccessible.

`supabase/tests/discovery-cities.sql` verifies accent-insensitive search, same-name cities across countries, query bounds/wildcards, reverse lookup validation, grants, anonymous access, city-area filtering, unknown venue exclusion, filter combinations, GPS-radius override and filtering before pagination. All session fixtures roll back. City service and local-preference unit tests cover response validation, permission failures, missing nearby cities, legacy migration and corrupt/failed local storage.
